DualTorch · 技术方案

让两颗变焦闪光灯一起亮 针对 vivo X300 Ultra（V2547A）的双 LED 手电筒实现路径与工程验证

系统手电筒只驱动一颗灯，相机却能同时点亮两颗。这不是权限问题，而是 Android 的 Flash 抽象与厂商 HAL 之间的缝隙。下面是从硬件事实、开源调研到可安装 APK 的完整推演。

01硬件事实：双灯是怎么被选中的

先把「变焦闪光灯」这个词拆开。它并不是真的能变焦，而是两颗发光角不同的 LED 组合出三种光斑：一颗大角度泛光、一颗窄角度聚光，中焦段两颗一起开、光斑叠加成一片均匀的柔光——vivo 把这套叠加算法叫「光斑融合」。

拍照模式下 15mm–48mm 用一个灯补光；48mm–85mm 以及 85mm 以上用两个灯补光。不管拍人像还是日常场景，都会自动调节。 vivo 官方社区 · X300 Pro 多焦段闪光灯答疑
机型灯珠布局官方焦段策略驱动方式
X200 Ultra上=广角主闪，下=长焦闪（窄光束，有效 4m）50mm 以下主闪；50–135mm 启用下方长焦闪单颗双通道 LED 驱动 IC，通道选择由相机 HAL 的闪光算法按焦段决定
X300 Pro双灯 + 光斑融合，覆盖 24 / 50 / 85mm<48mm 单灯；≥48mm 双灯
X300 Ultra同代全焦段方案长焦段双灯

关键结论：「点亮哪几颗」这个决定发生在 HAL 内部，不在 App 层。应用能看到的只有一个布尔值 FLASH_INFO_AVAILABLE。

02为什么系统手电筒永远只亮一颗

Android 的相机栈里，闪光灯是挂在 camera device 上的属性，不是独立设备。所以：

  • CameraManager.setTorchMode(cameraId, true) 一次只能指定一个 cameraId；
  • 同一个 cameraId 的 torch 请求，HAL 内部映射到固定的那一路通道（通常就是主闪）；
  • Android 13 加的 turnOnTorchWithStrengthLevel() 只调电流档位，不换通道；
  • SystemUI 的手电筒磁贴更简单——只取第一个后置带闪光的相机。

03开源调研：为什么没有现成轮子

GitHub 上做手电筒的项目很多，但绝大多数停在 setTorchMode 这一层。挑几个有代表性的：

项目做法对双灯的意义
danferns/lights 遍历所有带闪光灯的 cameraId，各自独立开关，宣称可同时点亮前后闪光灯，且不需要相机权限 部分只有「长焦相机也上报了 Flash 单元」时才能双亮；vivo 这类单 Flash 单元 + 双通道 IC 的结构它无能为力
InkAssists/torch-tile 用 setTorchMode 包一个快捷设置磁贴，绕开 Android 16 坏掉的系统手电筒磁贴 无纯 UI 封装，通路不变
30n1ne/1tourch Camera2 强度档位做 1–5 级调光 间接只能调电流，不能选通道
PDDStudio/easyflashlight 等 对 Camera2 torch 的库封装 无同一层 API 的再包装
AOSP SystemUI · FlashlightController 取第一个后置带闪光的相机，调 setTorchMode 无官方实现本身就只点亮一颗
内核 leds-flash / leds-class-flash MTK/高通平台导出 led:torch_0、led:torch_1、led:switch_0 等节点，直接 echo 数值即可分通道点亮 能唯一确定性的办法，但要 root
调研结论：没有现成项目解决这个问题，因为它们全都待在 App 层，而「点哪颗灯」的决定权在 HAL。要突破，只有两条路——让 HAL 自己决定（复刻相机的请求链路），或者绕过 HAL（root 写 sysfs）。

04四条通路，按可行性排序

通路原理门槛成功率
① 相机会话 + 焦段联动 建一路预览流，重复请求里设 FLASH_MODE_TORCH、CONTROL_AE_MODE，并把 CONTROL_ZOOM_RATIO 拉到 2× 以上。HAL 的闪光算法会按焦段重新算通道组合 相机权限 最有希望
② 多相机系统手电 遍历 cameraId 逐个 setTorchMode，若长焦相机也注册了独立 Flash 单元，就可能点亮第二颗 无 看厂商
③ Vendor tag 注入 从 getAvailableCaptureRequestKeys() 里找 com.vivo.* 私有 key，直接塞进请求。部分厂商会开放 flash 相关 tag 相机权限 + 正确的 key 看 HAL
④ Root 写 sysfs echo N > /sys/class/leds/led:torch_1/brightness，两路通道完全独立可控 root 确定

为什么①真的可能奏效

vivo 的「双灯」不是一个独立的开关，而是相机拍照链路里算出来的结果。它的输入至少包括当前焦段、AE 模式、场景亮度。当 App 用完整 capture 请求把这三样都喂进去时，HAL 没有任何理由区别对待「相机 App」和「第三方 App」——除非它在 framework 层加了白名单。

// CameraSessionEngine 的核心：把 HAL 需要的上下文凑齐
builder = device.createCaptureRequest(TEMPLATE_PREVIEW);
builder.addTarget(reader.getSurface());
builder.set(CONTROL_AE_MODE, CONTROL_AE_MODE_ON);
builder.set(FLASH_MODE,     FLASH_MODE_TORCH);
builder.set(CONTROL_ZOOM_RATIO, 3.0f);   // ← 关键：让 HAL 以为你在用长焦
session.setRepeatingRequest(builder.build(), null, handler);

App 里把焦段做成了实时滑杆：会话保持期间拖动它，请求会重新下发，可以亲眼看到第二颗灯在哪个倍率被带起来。这个临界点就是这台机器最真实的证据。

05工程实现

四层结构

UI 层：双通道开关、策略切换、亮度/焦段/频闪、实时日志。
调度层：TorchController 负责四条通路的互斥与降级——系统手电和相机会话不能同时占用同一颗相机，切换时要先释放再点亮。
引擎层：四个独立引擎，各自封装一条通路。
探测层：把相机能力、私有 key、sysfs 节点全部打印出来，供人工判断。

几个必须处理的坑

· 相机会话需要一路真实 surface，用 ImageReader 持续丢弃帧维持管线；
· 预览尺寸必须从 StreamConfigurationMap 里挑，硬编码 640×480 在部分机型上直接抛异常；
· 系统手电会占住相机，切到会话模式前必须先 setTorchMode(false) 并等 HAL 释放；
· root 检测会阻塞（Magisk 还弹授权框），必须放后台线程，否则首屏就 ANR。

界面

主界面三个区：两个光源通道卡片（A 主闪 / B 变焦闪）、策略与参数、调试日志。日志是刻意放大的——这个工具的成败完全取决于你能否从日志里看出哪条通路真的把请求送到了 HAL。

06真机反馈与修正

X300 Ultra（V2547A，Android 17）第一次实测：策略选「相机会话」，只开 B 通道，滑杆放在 1.0×，结果两颗灯一起亮了。

原因很直接：代码里为了让 B 生效，把 zoom 顶到了 max(zoom, 2.0)。而 2.0× 对应 48mm，正好踩在 vivo 的双灯阈值上。主摄会话里 HAL 只有「单灯 / 双灯」两种结果，不存在「只点长焦」这个选项 —— 这不是 bug，是我把 A/B 的语义设计错了。

现象真实原因v1.1 修正
只要 B，却两颗都亮 主摄会话按焦段决策，2.0× 已进入双灯区间 只开 B 时自动切到长焦相机自己的会话（zoom=1.0 即该镜头原生焦段）；长焦不可直开则回退主摄并明确提示
不知道 HAL 到底给不给单独点长焦 之前没有手动指定会话相机的入口 会话相机改为 自动 / 主摄 / 长焦 三选一，三种组合都能试
亮度只有一个「默认」 API 33 的强度接口只作用于 setTorchMode，会话里没有 接入 FLASH_STRENGTH_LEVEL（API 35），预览流里直接下硬件档位

亮度控制的三种实现

方式API作用范围质量

滑杆的百分比会按 1 + round((max-1) × p/100) 映射到硬件档位；max=1 说明这颗闪光灯不支持调流，系统手电模式自动退回脉冲调光，会话模式则在界面上直说「调不了」—— 不假装能调。

// 会话内调光：Android 15 起才有的 key
int max = chars.get(CameraCharacteristics.FLASH_TORCH_STRENGTH_MAX_LEVEL);
if (max > 1 && percent > 0) {
    builder.set(CaptureRequest.FLASH_STRENGTH_LEVEL, 1 + round((max - 1) * percent / 100f));
}

07真机验证 SOP

  1. 看清单。进「硬件探测」，确认有几颗相机上报 flash=YES，以及 maxLevel 是否大于 1。两颗以上 → 通路②有机会；只有一颗 → 直接走通路①。
  2. 粗暴测试。探测页点「全开」，对每颗相机同时下发 torch，用眼睛看亮几颗。这是最快的分水岭。
  3. 会话测试。回主界面，策略切「相机会话」，焦段先放 1×，点「双灯全开」——应该只有一颗亮；再把滑杆推到 3×–4.6×，看第二颗是否亮起。
  4. 扫私有 key。如果③没反应，把探测页里的 com.vivo.* 键逐个试：主界面填 key/value 点「注入」，观察灯的变化。名字里带 flash / torch / led / dual 的优先。
  5. 记录临界点。把「第二颗灯开始亮的倍率」和「生效的策略」记下来，这就是这台机器的最终答案。
必须接受的边界：未 root 的情况下，能不能双亮完全取决于 vivo 的 HAL 有没有把这条路径开放给第三方。本工具不能保证成功，它保证的是把四种可能都试一遍，并且让你看得见结果。若四条通路全部失败，剩下的选项只有 root、或者向 vivo 申请私有 SDK。

剩下三条路：向 vivo 影像开放平台申请私有 Camera SDK（需企业资质）；用 LSPosed 在 HAL 客户端侧 hook（需 root）；或者退一步——用相机 App 的 3× 变焦 + 闪光灯常亮模式，把「拍照」当成手电筒用。

09第二轮复盘：四条通路全灭之后

1.1 版在 X300 Ultra（V2547A，Android 17）上实测的结果是：所有通路都失败。具体表现是「不管只开 A 还是只开 B，两颗灯一起亮」，亮度滑杆也毫无反应。这不是参数没调对，而是我把「应用层能控制到什么粒度」这件事想错了。下面是复盘用的证据链。

证据原文 / 事实推论
vivo 官方社区（X200 Ultra） 「后置配备两颗闪光灯……会根据不同拍摄焦段自动协同工作」；上方灯 0.6–2.2×，下方灯 2.2–4× 为长焦灯，中间是多光谱传感器。用户追问「如何切换另一个或两个全亮」，官方答复是「把建议收集记录」。 厂商没有提供手动切换单灯的入口，这是产品定义，不是遗漏。
vivo 官方答疑（X300 Pro） 「15–48mm 只用一颗，48–85mm 用两颗」。 选灯是相机 HAL 的闪光算法按焦段算的，只发生在「拍照闪光」这条链路里。
AOSP Camera2 CameraManager 只有 setTorchMode(cameraId, on) 和 turnOnTorchWithStrengthLevel(cameraId, level)；粒度是 cameraId，一个 cameraId 对应一个 Flash 单元。 应用层根本没有「第几颗 LED」这个参数可传。
Linux 闪光灯驱动 高通 leds-qcom-flash 导出 led:torch_0/1、led:flash_0/1；联发科 flashlight_core 的 flashlight_strobe 命令是 TYPE CT PART LEVEL DURATION，PART 才是灯路。 「单灯」这个粒度只存在于驱动层。HAL 之上被合并成了一个开关。
GitHub kailashrs/camx-fullsize X200 Ultra 的 KernelSU 模块：靠改 /vendor/etc/camera/camxoverridesettings.txt、改 vendor.camera.aux.packagelist 才能让第三方 App 看到隐藏的物理相机。 vivo 连「物理相机」都对第三方隐藏，更不会单独暴露一颗灯。绕开它必须 root + 改 HAL 配置。
开源手电 App（danferns/lights 等） 实现都停在 setTorchMode 循环遍历 cameraId 这一层。 社区里没有现成方案，因为它们也到不了 HAL 内部。
结论：「只点长焦那颗」在无 root 的应用层是做不到的。torch 这条链路在 HAL 里就是「整组 LED 一起开」，两颗灯同时亮是符合设计的行为，不是 bug。我前两版让你去调焦段、换会话相机，方向本身就错了。

亮度为什么也没反应

应用层调亮度只有一条合法路径：turnOnTorchWithStrengthLevel（API 33）/ FLASH_STRENGTH_LEVEL（API 35）。它能不能生效，取决于 HAL 有没有上报 FLASH_INFO_STRENGTH_MAXIMUM_LEVEL > 1，以及驱动有没有真的按档位改电流。1.1 版在 max=1 时会自动退到「30Hz 脉冲调光」，而 setTorchMode 单次调用就要几十到上百毫秒 —— 30Hz 根本跑不起来，看起来就是「拖了没反应」。这是我自己引入的假象，2.0 已经删掉。

2.0 改成「先证明，再谈控制」

与其继续猜，不如把这件事做成一次可复现的实验：把每个候选 cameraId 逐个点亮，由用户肉眼确认亮了几颗，再把亮度档位设下去并回读，最后给出结论。整个过程 1 分钟，结论只有三种：

自检结果含义下一步
某个 cameraId 只亮一颗HAL 确实拆开了单灯通道可用把系统手电指到那个 id，单灯就成立
所有 cameraId 都两颗都亮torch 被绑到整组 LED无 root 到此为止；要单灯只能走驱动层
全部点不亮相机被占用，或厂商禁用了第三方 torch关掉相机 App / 重启后再测

亮度同理：设最高档 → 回读；设最低档 → 回读；再问用户「变暗了吗」。如果回读变了但灯没变，说明 HAL 只是接受了参数、没落到驱动电流上 —— 这种「假支持」只有靠肉眼才能识破。

// 2.0 的判定逻辑（简化）
setTorchLevel(id, max);  readAtMax = getTorchStrengthLevel(id);
setTorchLevel(id, 1);    readAtOne = getTorchStrengthLevel(id);
// 回读一致 + 肉眼无变化  => HAL 接受了档位，但没落到电流
// 回读一致 + 肉眼变暗      => 真支持
// 回读报错/恒为 -1        => 系统不支持

如果自检证明「做不到」，还剩什么

  1. Root + 驱动节点。高通写 led:torch_0 / led:torch_1 的 brightness；联发科写 flashlight_strobe 的 PART 参数。这是唯一确定能分开两颗灯的方式，2.0 的「Root 直控」页就是干这个的。
  2. 等 vivo 开放私有接口。目前没有公开的影像 SDK 提供闪光灯通道选择。
  3. 退一步。用 vivo 相机在 ≥50mm 拍一张带闪光的照片 —— 那一刻 HAL 点的确实是下面那颗长焦灯，只是它只闪一下。

10第三轮：真机自检的实测结果

2.0 的自检在 X300 Ultra（V2547A，Android 17，无 root）上跑完了。结果不是「全灭」，而是一个很具体的形状：单灯通道存在，但只属于上面那颗。

观察推论
camera 0 的 torch 只点亮上面那颗 HAL 在 torch 通路上确实只驱动了单颗 LED，而且是主补光那颗。这也是普通手电筒该有的行为 —— 之前的「两颗一起亮」只发生在相机会话里。
22.5mm 长焦物理相机 invalid cameraId 它不在 getCameraIdList() 里，CameraManager 直接拒绝。长焦灯在 torch 通路上不可寻址，不是参数问题。
档位 5 被拒 厂商上报的 FLASH_INFO_STRENGTH_MAXIMUM_LEVEL=5 是单次闪光的档位表；torch 实际校验的范围更小。声明与校验不一致，必须实测。
相机会话 2.0× 会双亮，系统手电只亮一颗 两条链路不同：setTorchMode 是 CameraService 的捷径，直接映射到主 LED；相机会话把请求交给 HAL 的闪光算法，按焦段决定点几颗。

v2.1 的四处修改

问题改法
亮度档位「声明一套、校验另一套」 probeMaxLevel() 从声明值往下逐档真调，返回第一个被接受的档位；只接受 1 档就直接判定「不能调光」，不再给假滑杆
不知道 HAL 有没有留私有 tag 报告里全量导出 getKeys() / getAvailableCaptureRequestKeys() 中含 flash/torch/led/strobe/light/vivo 的 key 与值
长焦相机不可寻址 新增物理子相机会话：OutputConfiguration.setPhysicalCameraId("5") + createCaptureSessionByOutputConfigurations + FLASH_MODE_TORCH，这是唯一能「指名」长焦相机的合法 API
无法确认长焦灯是否还活着 新增单次闪光：主摄 3× + FLASH_MODE_SINGLE，HAL 会两颗一起闪 —— 灯是好的，只是不能常亮
到此为止的确定结论：无 root 时，应用层能拿到的最大粒度是「camera 0 的上面那颗」。
长焦灯在 torch 通路上没有入口；物理子相机会话是最后一个可能，若 HAL 也不认，就只剩 root 或 vivo 私有接口。

为什么「物理子相机会话」还值得一试

Camera2 的 Logical Multi-Camera 允许把某个 output 绑定到 physicalCameraId 上。虽然 setTorchMode("5") 被拒，但会话建立后，请求会带着「这条流属于 camera 5」的信息进入 HAL。如果 vivo 的闪光算法是按流所属物理相机选灯，而不是按逻辑相机的焦段，那这里就能单独点亮长焦灯。反之，如果 HAL 在 configureStreams 阶段就拒绝物理流，日志会直接写配置失败 —— 两种结果都能一次看清。

OutputConfiguration oc = new OutputConfiguration(surface);
oc.setPhysicalCameraId("5");                     // 指名长焦
device.createCaptureSessionByOutputConfigurations(List.of(oc), cb, handler);
// onConfigured 之后
builder.set(CaptureRequest.FLASH_MODE, CaptureRequest.FLASH_MODE_TORCH);

11接进系统入口：五个入口里能用的三个

目标很直接：不打开 App 也能开关手电、切灯路、切亮度。先把 vivo 给的五个入口逐个验证了一遍，结论是三个能接、两个接不了。

入口机制能否接第三方
控制中心 TileService，一个 App 可声明多个磁贴（每个磁贴一个 Service 子类） 可以在「编辑 → 全部开关」里拖入
快捷启动（长按音量减） 列表里有「打开应用 >」，绑到本 App 即可 可以熄屏可用，是唯一的熄屏入口
轻敲背面 vivo 官方说明含「打开应用（如相机）」选项 可以截图里只显示到上半段，往下滑有「打开应用」
锁屏右侧快捷入口 只列系统内置项：电话 / 计时器 / 计算器 / 录音 / 手电筒 / 相机 / 新建笔记 不行没有第三方入口，系统未开放 API
vivo 自带手电筒开关 系统 App 的私有实现，固定点 camera 0 的上面那颗 不行既不能替换也不能扩展

架构：所有入口只发命令，状态只有一个持有者

磁贴 / 快捷方式 / 通知按钮 / 冷启动
              │  一条 Intent（on / off / toggle / cycle_led / cycle_bright）
              ▼
       ShortcutActivity（零界面，收完立刻 finish）
              │  startForegroundService
              ▼
        TorchService  ←── 唯一持有 TorchController 的地方
              │
              ├── Prefs（灯路 / 亮度 / 开关，磁贴与界面共读）
              └── 低优先级通知（关灯 / 切灯路 / 调亮度）

几个必须踩过的坑：

坑处理
Android 12+ 禁止后台启动前台服务，磁贴里直接 startForegroundService 会抛异常 先试 FGS，失败则 startActivityAndCollapse 拉一个透明 Activity，由前台 Activity 再起服务
Android 14+ 前台服务必须声明类型 foregroundServiceType="specialUse" + FOREGROUND_SERVICE_SPECIAL_USE 权限
setTorchMode 的灯挂在进程上，进程被回收灯就灭 用前台服务持有，通知常驻；关灯时才 stopForeground + stopSelf
磁贴和界面各存一份状态，会互相打脸 只存 Prefs 一份，onResume 时对齐；主按钮改成「按预设开灯」而不是「按 A/B 开关」
三个磁贴要显示不同副标题 每个磁贴一个 TileService 子类，共用 BaseCmdTile 渲染逻辑

两个磁贴与四个快捷方式

入口动作副标题 / 说明
磁贴「双芯闪光灯」开 / 关广角 · 最亮 / 关闭（沿用上次设置）
磁贴「手电灯路」广角 ↔ 双灯当前灯路
快捷方式开/关、切灯路、切亮度、关灯长按图标；也会被「原子控件」面板收录。切亮度走这里，不占磁贴位
需要说清楚的一点：系统入口解决的是「少点两下」，不解决「点哪颗灯」。
上灯 / 双灯都能一键切换，但下灯（长焦那颗）依旧不可单独常亮 —— 那是 HAL 没暴露的通道，入口再多也变不出来。
